# 设计方案：独立核验员（Verifier）

状态：方案，未实现。依赖 PR #16（`feature/briefing-reliability-hardening`）和 Skill `5daee0b`。

## 1. 要解决什么

现在的多智能体流程里，事实只被"写的人"查过一次。审稿人（Reviewer）读的是已经写好的稿子、作者存下的来源和作者的笔记，
所以容易沿着作者的思路走。2026-11-06 的测试运行最后有三个问题没解决，都属于这一类：

- 稀土一项：把"2025 年已证实的暂停措施"和"现在是否延期（未核实）"混在一起；
- 六个公告的适用范围说宽了：只有四个是稀土，另外两个是超硬材料和锂电池；
- 未核实的事项被标成了"媒体报道"。

多智能体真正比单智能体强的地方，是**独立性**：另一个智能体不看作者的材料，自己去找原文，结论不一致就说明有问题。
这个方案加的就是这一步。

## 2. 一句话设计

研究阶段结束、主编动笔之前，系统自动挑出高风险说法，交给几个**看不到作者来源和笔记**的核验员。
核验员只拿到这句话本身，自己找原始文件并尝试推翻它。系统把结果和作者的说法比对：一致就记为"独立核实"；
不一致就生成一条审查意见（finding），走现有的返工和审稿流程。

不改变 Chief → Lead → Scout 的结构，也不让核验员改稿。它只提交证据和结论。

## 3. 在流程里的位置

```
计划 → 两条线研究（Lead + Scout）→ 合并到主编
     → 【新】说法核验（claim_verification）
     → 主编写稿 → 校验器 → 独立审稿 → 返工 → 二审 → 人工签发
```

- 触发：两位 Lead 的结果都已被接受并合并进主编目录后，由**控制器自动**启动，不由主编决定核验哪些、要不要核验，
  以免写的人挑自己有把握的去核。
- 主编提交初稿的前置条件里加一条：核验已结束（全部提交，或失败、超时并已记录）。
- 核验的结论作为输入交给第一位审稿人。

## 4. 核验哪些说法

由控制器按规则挑，规则写在 Skill 里，不写死在代码中：

1. Skill 校验器已经给每条说法打了风险分（`check_quotes.py`：legal 5、list 5、negative 4、statistic 3、
   company_response 3，分数 ≥ 3 为高风险）。高风险说法全部入选。
2. 决定一个事件状态标签的说法（会让事件显示为"官方确认"或"拟议"的那条）。
3. 被列为跨境（中美互相牵连）的说法。

上限：每次运行最多 12 条（`max_verified_claims`），每个核验员 3–4 条，最多同时 3 个核验员。超出的按风险分排序，
没轮到的在签发单上写明"未独立核实"。

## 5. "独立"怎么保证

核验员拿到的任务文件（`assignment.json`）只有：

- 说法原文，以及它声称的类型（法律 / 名单 / 数字……）和法律状态（已生效 / 拟议……）；
- 事件日期、报告的时间窗口和截止时间；
- 不包含作者的来源网址、引文、笔记，也不包含其他智能体的目录。

| 运行模式 | 隔离由谁保证 |
|---|---|
| sandbox（默认，macOS 已验证） | 新的 `verifier` 权限配置：只能写自己的目录，**读不到** `tasks/`、主编的账本和叙述；可以联网抓取网页 |
| container（现在的测试环境） | 没有操作系统级的文件隔离，只能靠指令约束。核验结论要标注"独立性未强制"，评估时单独统计 |

另一个隐患是**同一个模型的盲点相同**：作者和核验员都用同一个模型，可能犯同样的错。
可以给核验员配不同的模型或推理强度，作为可配置项（`verifier_model`），在第 9 节的评估里比较。

## 6. 核验员做什么、交什么

核验员沿用 Skill 现有的工具：用 `brief.py fetch` 保存原文（自动算哈希），用 `brief.py add-claim` 记录自己找到的
引文；交接检查会核对引文是否真的在保存的原文里。最后写 `verification.json`：

```json
{"results": [
  {"claim_id": "C002",
   "verdict": "confirmed | contradicted | scope_differs | status_differs | not_found",
   "found_status": "enacted | proposed | suspended | reported | unknown",
   "evidence": [{"source_id": "S001", "quote": "原文中的确切文字", "evidence_type": "official_document"}],
   "note": "查了什么、为什么这么判断"}]}
```

规则：

- 只有 `confirmed` 和 `not_found` 可以不附证据；其余三种结论必须附上自己保存的原文和引文。
- 优先找一手来源（政府公告、公司公告）；只找到媒体报道时，结论最多只能算"媒体佐证"，不能算独立确认。
- 不知道就写 `not_found`，不允许猜。

## 7. 结果怎么用

控制器（确定性代码，不靠模型判断）把核验结果和作者的说法比对：

| 核验结论 | 处理 |
|---|---|
| `confirmed`，且来源是一手的 | 说法记为"独立核实"。签发单上把它从需要人工重点看的清单里移到"已独立核实"一栏 |
| `confirmed`，只有媒体来源 | 记为"媒体佐证"，不改变标签 |
| `contradicted` / `status_differs` / `scope_differs` | 生成一条 finding（来源 `verify-N`，严重度 major，类别 `fact_status`），按出处（provenance）派给负责的 Lead 或 Scout |
| `not_found` | 记为"未能独立核实"；高风险的法律、名单类说法不能显示为"官方确认" |
| 核验员失败或超时 | 该说法记为"未核验"，不阻塞流程，原因写进运行摘要 |

核验生成的 finding 进入 PR #16 里已有的审查意见登记表，因此：

- 主编可以在写稿前发一次返工，最多一轮（`max_verification_rework`，不占用审稿后的返工次数）；
- 写稿前没解决的，作为"之前的意见"交给第一位审稿人，审稿人必须给出 resolved 或 unresolved 的判断；
- 现有规则不变：严重意见没解决，运行就不能标为"可交人工签发"（ready_for_human_review）。

**对报告标签的影响**（Skill 侧）：状态图例增加一种"未核实"的标记（灰色），专门用于 `not_found` 和没有来源的事项，
不再借用"媒体报道"的黄色。这同时解决了 11-06 审稿意见 review-3/R002（图例与证据不符）。

## 8. 成本

| 项目 | 设定 |
|---|---|
| 每个核验员上限 | 6 万新 token（11-06 审稿人每轮实际用了 4.3 万–8.4 万） |
| 每次运行最多 | 3 个核验员 + 1 次核验返工 |
| 预算预留 | 新增 `verification` 预留 15 万，研究阶段不能占用；用法同 PR #16 里的 synthesis/review/rework 预留 |
| 时间 | 每个核验员 20 分钟 |

按 11-06 运行的总量（约 50 万新 token）估算，每次运行增加约 20%–35%。这个数字是估计，要在评估里实测。

## 9. 怎么证明它有用

不上线真实运行，先在固定的样本上比较：

1. **样本**：3–5 个已结束的时间窗口，冻结网页快照，保证每次比较看到的内容一样。
2. **故意埋错**：在说法里放入这几类错误，各若干条：
   - 把"拟议"写成"已生效"；
   - 日期写错；
   - 适用范围写宽（照 11-06 的六个公告来做）；
   - 名单成员写错；
   - 把媒体说法当成官方说法。
3. **对比四组**，同一窗口、同一总预算：
   - A：只有审稿人（现状）；
   - B：审稿人 + 核验员；
   - C：B，但核验员换一个模型；
   - D：单智能体加同样的预算。
4. **看这些数**：
   - 埋的错被抓出的比例；
   - 误报（把对的说成错的）的比例；
   - 最终报告里标签的准确率；
   - 新 token 用量；
   - 人工签发要看的条数。

判断标准写在前面：B 抓错明显多于 A、误报可控、成本增加在 35% 以内，才值得默认开启；否则保留为可选开关。
不在评估用的样本上调提示词。

## 10. 要改哪些地方

**Nex**（预计 1.5–2 周）

- `briefing-contracts.ts`：新增 `verifier` 角色和 `verification.json` 的格式校验。
- `briefing-sandbox.ts`：`verifier` 的工具（只有 status、submit）和权限配置，拒绝读取 `tasks/` 和主编记录。
- `briefing-workflow.ts`：
  - 新阶段 `claim_verification`；
  - 按规则挑说法、分批启动核验员、判断失败和超时；
  - 比对结果并登记 finding；
  - 写稿的前置条件；
  - 运行摘要里加核验统计。
- `briefing-budget.ts`：新增 `verification` 阶段和预留。
- 测试：脚本化测试覆盖这些情况：
  - 结论一致；
  - 结论矛盾，走返工；
  - not_found 时标签降级；
  - 核验员超时；
  - 预算不足；
  - 重启恢复；
  - 核验员不能读作者目录（真实沙箱测试）。

**Skill**（预计约 1 周）

- `references/roles/verifier.md`：核验员的工作说明（第 6 节）。
- `references/roles/workflow.json`：`max_verified_claims`、核验预算、`max_verification_rework`、`verifier_model`。
- `brief.py`：渲染"独立核实 / 未核实"，图例加灰色"未核实"标记；签发单分栏。
- `check_handoff.py`：`verifier` 角色的交接检查（结论必须有证据）。
- 回归测试：上面每种结论对标签和签发单的影响；中文渲染不受影响。

**评估**（约 1 周，加人工标注时间）：第 9 节。

## 11. 不做的事

- 不让核验员改稿或改账本，它只交证据和结论。
- 不让智能体之间辩论或投票。
- 不用核验结果代替人工签发；"独立核实"不等于"已确认无误"。
- 不提高返工次数来换通过率。

## 12. 待定的问题

1. 法律、名单类说法 `not_found` 时，是降级标签（本方案的建议），还是直接阻止报告标为"可交人工签发"？
2. 核验员是否默认用不同的模型？取决于评估结果和账号额度。
3. 测试环境在 container 模式下没法强制"看不到作者材料"。是否先在 macOS sandbox 模式下做评估？
4. 核验条数上限 12 条够不够？要看实际运行里高风险说法一般有多少条。
