# 设计方案：实时监测（Monitor）

状态：方案，未实现。依赖现有的多智能体流程（`main`）和 Skill 的 `discover.py`；第 2 层复用
[独立核验员方案](briefing-verifier-design.md)，那个方案做完之前，快报只有审稿、没有核验。

## 1. 要解决什么

项目名里有"实时监测"，但现在只有周报：每周跑一次，平时没人看着。漏掉和迟到的风险主要在两类事情上：

- **有截止日的事项。** `active_cases.md` 里，A001（BIS 关联方规则的暂停期，11-09 截止）和 A002（中国稀土出口措施的
  暂停期，11-10 截止）都有明确的截止日。截止日当天发没发公告，是管理层最关心的消息，但周报可能要过好几天才写到。
- **突发的官方动作。** 比如实体清单新增公司、商务部发布新公告。（海关总署现在不在来源清单里，要不要加见第 14 节。）

"实时"在这里的意思要说清楚：政策消息发得不多，渠道和时间也基本固定（联邦公报每个工作日更新，商务部有公告页），
所以**几分钟到一小时内发现就够了**，不需要做到秒级。真正要做到的是：**不漏、不迟、来源断了要知道**。

## 2. 一句话设计

一个**不调用模型**的值守程序按固定频率扫已有的那些来源，只记下新出现的条目。有新条目时，先交给一个小的分诊员判断要不要紧。
只有"要紧"的才启动一次缩小版的多智能体运行，出一份快报，交人工签发。平时攒下的条目，作为下一次周报的起点。

不改 Chief → Lead → Scout 的结构，也不让任何智能体自己决定要不要启动运行。启动由控制器按规则决定。

## 3. 三层结构

```
第 0 层  值守程序（确定性代码，0 token）
         定时扫来源 → 去重 → 新条目 / 来源异常 / 截止日提醒
              │ 有新条目
              ▼
第 1 层  分诊员（小模型，每批一次）
         相关吗？对应哪个 active case？级别：忽略 / 留给周报 / 快报
              │ 快报（或规则直接判为快报）
              ▼
第 2 层  快报运行（缩小版的现有流程）
         主编 + 一侧的 Lead + 1–2 个 Scout + 核验员 + 审稿人 → 快报 → 人工签发
```

每往下一层，花费大约多一个数量级，触发也更少。这样设计的原因是：**大部分时间什么都没发生，没发生的时候就不应该花钱。**

## 4. 第 0 层：值守程序

**复用而不重写。** `discover.py` 已经能扫 `discovery_sources.json` 里的官方 API（联邦公报、DOJ）、10 个官方公告页、
6 个 RSS，以及按日期限定的新闻搜索，还会记录每个来源能不能访问（`discovery_log.json`）。值守程序要做的是给它加一个
增量模式：

```sh
python3 -I scripts/discover.py --monitor --state monitor/state.json --tiers official --out monitor/batches/<时间>
```

- **去重**：每个条目按"去掉跟踪参数后的网址 + 标题"算一个指纹，存在 `monitor/state.json`。公告页另外记整页正文的哈希。
  如果页面变了，但解析不出新的条目，也记为"页面有变化"，交分诊员看一眼。
- **分档扫描**（频率写在 Skill 的 `references/monitor.json` 里，不写死在代码中）：

| 档 | 来源 | 默认频率 |
|---|---|---|
| official | 联邦公报 API、DOJ API、BIS / OFAC / USTR / 商务部 / 国务院 / 工信部 / 网信办等官方公告页 | 每 30 分钟 |
| feeds | 公司和媒体的 RSS（NVIDIA、AMD、FT、SCMP 等） | 每 2 小时 |
| news | 按日期限定的新闻搜索 | 每天 3 次 |
| deadline | 截止日前 72 小时内，相关案件指定的来源 | 每 15 分钟 |

- **截止日日历**：`active_cases.md` 的"Next check"一列现在是自由文字，程序读不了。Skill 侧需要给每个案件加一个机器能读的
  `deadline`（日期 + 时区）和 `watch_sources`（看哪些来源）。之后值守程序会这样做：
  - 截止前 72 小时，自动提高这些来源的扫描频率；
  - 截止时间一过，如果没有扫到相关公告，生成一条"截至某时某刻检索，未见公告"的提醒。
  这条提醒只说明检索的结果，不能写成"没有延期"。"没有新闻"不等于"状态没变"，这是 `watchlist.md` 已有的规矩。
- **来源健康**：一个官方来源连续 6 小时访问失败，或连续 3 次返回空列表，就单独报警。来源断了而没人知道，
  比漏一条新闻更危险。
- **在哪里跑**：放在 Nex 服务端，新建 `briefing-monitor.ts`，用一个计时器驱动，做法和 `schedules.ts` 一样：
  从触发时刻算下一次，机器睡眠醒来后只补跑一次。它按现有控制器脚本的方式调用 Python（`python3 -I`），把输出当数据读，
  **不是智能体，也不开对话**。
- **访问规矩**：和 `discover.py` 现在一样，被拒绝就记录、跳过，不绕过付费墙和访问限制。同一个网站的两次请求之间
  至少间隔 `min_interval_per_host`。

输出：每批写 `monitor/batches/<时间>/items.json`，同时往 `monitor/log.jsonl` 追加一行（扫了什么、新增几条、哪些来源失败）。

## 5. 第 1 层：分诊员

只在一批里有新条目时才启动。新增一个 `triage` 角色：

- **能看到的**：只有这一批的 `items.json`、`active_cases.md`、`watchlist.md` 和 Skill 的说明。读不到历史运行和其他目录。
- **能用的工具**：只有 `briefing_submit` 和 `briefing_status`；权限配置的写法和 scout 一样，只能写自己的目录。
- **交什么**：`triage.json`，每个条目一行：

```json
{"items": [
  {"item_id": "…", "level": "drop | digest | flash",
   "case_id": "A002", "domain": "policy", "side": "cn",
   "reason": "商务部公告页新增一条，标题提到稀土出口管制措施的暂停期"}]}
```

分诊员只给级别，不写事实。它的判断不会进入报告。

**规则先于模型。** 有些情况不需要模型判断，控制器直接定级：

| 情况 | 级别 |
|---|---|
| 官方来源的新条目，命中某个 active case 的 `watch_sources`，且在它的截止窗口内 | flash |
| 截止时间已过，未见公告 | flash（快报的任务是确认"到底有没有发"） |
| 官方来源连续失败 | 只发提醒，不启动运行 |
| 只有聚合站链接、找不到原始来源 | 最高 digest |

模型默认用小模型或低推理强度（`triage_model`），每批的 token 上限是 3 万。**30 分钟内同一个案件或同一个事件的多条条目合并成一批**，
避免一条消息被几个来源同时报道、触发好几次运行。

## 6. 第 2 层：快报运行

在 `briefing_start` 里增加一种模式 `flash`，由控制器启动，智能体不能自己启动：

- **窗口**：从上一次快报或周报的截止时间，到现在。
- **起点**：不跑 discovery 全扫，而是把触发这次快报的条目和分诊理由写进本次运行的 `discovery/candidates.md`。
  主编本来就读这个文件，scout 的权限也已经允许读 `discovery/`。
- **规模**（写在 `workflow.json` 的 `flash` 配置里）：
  - 主编；
  - 只派相关那一侧的 Lead；只有跨境事项才派两侧；
  - 每个 Lead 最多 2 个 Scout；
  - 核验员：核验员方案做完后加入，最多核验 4 条；
  - 审稿人 1 轮，返工最多 1 轮。
- **产出**：Skill 新增一个快报模板，一页以内，内容是：
  - 发生了什么；
  - 法律状态（官方 / 媒体 / 拟议 / 未核实）；
  - 对应哪个 active case；
  - 还不知道什么。
  校验、出处检查、人工签发这些规则都照旧。
- **通知**：运行结束后，在这个账户的"监测"项目对话里发一条消息，附上快报和状态。**快报只是交给人看，不会自动发给任何人。**
- **排队**：同一时间只跑一次快报，后面来的排队。Nex 限制每个对话最多 8 个子对话同时运行，快报要遵守这个限制。
  如果周报正在跑，快报就等着，或者把条目留给周报。

## 7. 和周报的衔接

- 下一次周报开始时，把这一周内 `digest` 和 `flash` 级别的条目，加上已签发的快报，并入周报的 `discovery/candidates.md`。
  周报照常扫一遍，确保监测漏掉的东西也能补上。
- 快报里已经接受的说法，可以按 [研究设计](briefing-research-design.md) 第 2 项（跨运行证据库）的规则，在周报里作为
  **沿用**（carried over）引用：日期保持原来的，标明是沿用，不能算作本周的新证据。
- 截止日提醒，以及快报得出的结论，会更新 `active_cases.md` 的"Last known"一列，但仍然标为"待下次核实"。

## 8. 刹车和限额

| 项目 | 默认值 | 超出后 |
|---|---|---|
| 每天的分诊 token | 30 万 | 当天剩下的批次只按规则定级，不再调用模型 |
| 每天的快报次数 | 2 次 | 其余降为 digest，在监测对话里说明 |
| 每次快报的新 token | 30 万 | 沿用现有预算机制：到上限停止任务，运行结束为 `budget_exhausted` |
| 免打扰时段 | 不设（可配置） | 免打扰时段内只记录，到点再处理；截止日提醒不受影响 |
| 同一事件的冷却期 | 6 小时 | 冷却期内同一事件的新条目并入下一次周报 |

预算的估算依据是 11-06 那次运行，各角色用的新 token：主编 10.3 万，Lead 6.4–8.7 万，Scout 2.2–4.1 万，三轮审稿共 18.7 万。
快报只用一侧 Lead、一轮审稿，估计 20–30 万。这个数字是估计，第 10 节的阶段 2 会实测。

## 9. 部署前提

- **需要一台一直开着的服务器。** 笔记本合上就停了。监测只适合部署机，开关是 `NEX_BRIEFING_MONITOR=1`，默认关闭。
- **沙箱**：部署机是 Linux，沙箱是否生效还没验证（ROADMAP 的 MAS-03）。在 container 模式下，分诊员和快报智能体之间
  没有文件隔离，运行摘要里要写明这一点，这和核验员方案的处理方式一样。
- **账户隔离**：每个账户有自己的工作区，`monitor/state.json` 和监测对话也按账户分开。

## 10. 分阶段做，每一阶段都有"值不值得继续"的判断

| 阶段 | 做什么 | 继续的条件（事先写好） |
|---|---|---|
| 0（约 1 周） | 只做第 0 层：增量扫描、去重、截止日日历、来源健康。结果每天在监测对话里发一个"新官方条目"列表，不调用模型 | 影子运行 2 周后：官方来源去重后，平均每天的新条目不超过 30 条；官方条目从发布到发现，中位数在 1 小时以内 |
| 1（约 1 周） | 加分诊员和规则定级 | 人工抽查分诊结果：该判为 flash 的漏判为 0；误判为 flash 的不超过三成 |
| 2（约 1.5 周） | 加 `flash` 模式、快报模板、通知和排队 | 回放和影子运行中，快报能在规定预算内走到 `ready_for_human_review`，人工认为至少一半的快报"确实需要当天知道" |
| 3（约 0.5 周） | 接上周报（第 7 节） | 周报的召回率不下降，重复抓取的次数减少 |

如果阶段 0 的噪音太大，或者人工看那个列表就够用，阶段 1、2 就缩小甚至不做。这本身也是一个有用的结论。

## 11. 怎么证明它有用

- **回放**：联邦公报和 DOJ 的 API 可以按日期查历史，能把过去几周按时间顺序"重放"，离线测去重、规则定级和截止日提醒，
  不花 token。官方公告页没有历史版本，没法回放，只能靠阶段 0 的 2 周影子运行。
- **参照**：事先由人列一份那几周的事件清单（和核验员方案、研究设计第 4 项共用），作为标准答案。
- **看这些数**：
  - 延迟：从官方发布到发出提醒隔了多久，按来源分别统计；
  - 召回率：对照人工清单，第 0 层看到了多少，第 1 层把多少判为该判的级别；
  - 误报率：被判为 flash，但人工认为不需要当天处理的比例；
  - 每天的 token 和请求数；
  - 来源健康：报警次数，其中多少是真的断了。
- 规矩和其他方案一样：不在评估用的那几周上调提示词或规则；每个阶段的结果都要记录下来，没达标的也要记。

## 12. 要改哪些地方

**Nex**

- 新建 `briefing-monitor.ts`：计时器、分档、状态文件、批次合并、来源健康、每日限额、排队，以及在监测对话里发消息。
- `briefing-contracts.ts`：`triage.json` 的格式校验。
- `briefing-sandbox.ts`：`triage` 角色的权限配置和工具清单。
- `briefing-workflow.ts`：
  - `flash` 模式：由控制器启动，不跑 discovery，用指定的候选条目；
  - 只派一侧 Lead 的规则；
  - 快报的最终状态。
- `briefing-budget.ts`：快报的预算方案和每日上限。
- `server.ts`：在 `NEX_BRIEFING_MONITOR=1` 时接上监测。
- 测试：用脚本化的提供方和假的来源来测：
  - 去重；
  - 页面变了但没有新条目；
  - 截止日前加密扫描、截止后未见公告；
  - 来源连续失败时报警；
  - 规则定级；
  - 合并批次；
  - 每日限额；
  - 快报排队、和周报冲突；
  - 重启后不重复触发。

**Skill**

- `discover.py`：增加 `--monitor` / `--state` / `--tiers`；输出新条目、页面变化和来源状态。
- `references/monitor.json`：分档频率、每个网站的最小请求间隔、限额、免打扰时段、冷却期。
- `active_cases.md`（或新增 `active_cases.json`）：给每个案件加 `deadline` 和 `watch_sources`。
- `references/roles/triage.md`：分诊员的说明。
- `brief.py`：快报模板（中英文）；校验器允许小时级的窗口。
- 回归测试：截止日提醒的措辞（"未见公告"不能写成"未延期"）、快报模板的渲染和校验。

## 13. 不做的事

- 不让智能体长时间开着去搜，也不让智能体自己决定启动运行。
- 不自动发送快报，人工签发的规则不变。
- 不抓社交媒体，也不绕过访问限制。新增来源时，先确认对方允许机器访问。
- 不把"没扫到"写成"没发生"。
- 不在第 0 层没跑出数据之前，就去做第 1、2 层。

## 14. 待定的问题

1. "截止已过、未见公告"要不要直接启动快报，还是先只提醒、由人决定？本方案的建议是启动快报，因为这正是管理层要问的问题。
2. 快报发到哪里？现在只放在 Nex 的监测对话里。要不要接邮件或企业 IM，属于对外发送，需要单独决定。
3. 联邦公报有"预公开"（public inspection）文件，比正式刊登早一天左右。要不要加进 official 档？加之前要核对 API 现在的
   接口和使用条款。
4. 快报的窗口是小时级的，而 `brief.py` 和校验器现在都按日期处理窗口。是改成支持小时级窗口，还是快报一律按"当天"出？
5. 分诊员默认用哪个模型、什么推理强度，要看账号额度和阶段 1 的抽查结果。
6. 要不要把海关总署的公告页加进 official 档？中国一侧的出口管制公告有一部分是商务部和海关总署联合发布的。
